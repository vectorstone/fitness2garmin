# 把五年的 Apple Watch 健身数据完整搬进 Garmin Connect

> 一次真实的数据迁移记录：981 条训练、五年历史、零失败。顺便把过程中的六个坑（两个足以让任何现成教程方案翻车）完整记下来。
>
> 后面补了一章续篇：[Keep 的历史也找回来了](#续章把-keep-的历史找回来)，又踩了两个新坑。
>
> 配套工具已开源：[fitness2garmin](https://github.com/vectorstone/fitness2garmin)。

## 背景

我戴了几年 Apple Watch，最近换成了 Garmin。新表很好，但五年的跑步、骑行、力量训练历史还锁在苹果健康里。Apple Watch 换机不丢数据的前提是继续用 Apple 生态，而 Garmin 那边只认自己的格式。

Garmin Connect 网页端有个「导入数据」入口，但只接受 Fitbit 格式的 CSV，而且一次只能导一年、只有每日汇总（步数/体重），**训练活动本身根本进不去**。手动试过一些第三方方案，结果导入了一堆残缺数据——有轨迹没心率、时长对不上的碎片，一度想放弃。

于是决定自己搭一条流水线：**提取 → 转换 → 批量静默上传**。

## 先说结论

- 没有任何现成工具能一步到位，但三段各有成熟组件，组装起来比想象中可靠
- 最终 789 条训练 + 68 条体重记录全部迁移成功，0 失败、0 重复，顺带清掉了 127 条历史残留碎片
- 全程踩了六个坑，每一个都值得单独记录——如果你也想做同样的事，大概率会全部遇到

## 调研：为什么没有现成工具

动手前我把 GitHub 上能找到的相关项目扫了一遍（36 个候选逐个读源码验证），生态现状是：

1. **上传库的格局在 2026 年洗过一次牌**。曾经的事实标准 `garth` 在 2026 年 3 月被官方废弃——Garmin 改了认证流程，Cloudflare 对旧 SSO 端点直接 429。现在能用的只有 [python-garminconnect](https://github.com/cyberjunky/python-garminconnect) 0.3.20+（模拟移动端 TLS 指纹，活跃维护）。所有还依赖 garth 的老教程和老项目，登录环节已经全灭。
2. **Garmin 官方 API 帮不上忙**。2026 年 10 月新开的官方 Personal API 是只读的；Health API 的写入权限只对企业合作开放。个人用户的「调 API 上传」实际就是走非官方客户端，和你手机上的 Garmin Connect App 打同一套端点。
3. **每日指标是死路**。步数、睡眠、HRV 没有任何 API 写入通道（官方非官方都没有），能写的只有体重/身体成分。凡是宣称能把每日数据同步过去的工具，要么走网页导入，要么在吹牛。
4. **解析侧没有好用的**。Apple 的 `export.xml` 有两个陷阱：训练心率被聚合成 ~15 分钟块（所以必须用 Record 级心率样本重新贴回训练窗口）；GPS 轨迹单独放在 `workout-routes/*.gpx`，靠 `<Workout>` 里的 FileReference 关联。现有的解析器要么只出 CSV，要么内存爆炸。

所以方案定型为：**自己写流式解析器 + 官方 garmin-fit-sdk 编码 + python-garminconnect 上传**，再加一层比对计划保证幂等和增量。

## 流水线设计

```
export.zip ──流式解析──▶ workouts.json ──FIT 编码──▶ data/fit/*.fit
                │                                          │
                │                                     比对计划 plan.json
                ▼                                          │
        Garmin 现有活动清单 ◀──inventory──┘          upload / replace / skip
                                                           │
                                              静默批量上传（token 缓存、
                                              409 去重、2s 节流、SQLite 账本）
```

几个关键设计决策：

- **解析必须流式**。我的 `export.xml` 解压后约 700MB，全量加载必死。用 `iterparse` 两遍流式（第一遍收训练，第二遍收窗口内心率），内存峰值稳定在几十 MB。
- **心率归属**。心率样本按时间窗口挂回训练——这个看似简单的逻辑后面藏着坑 3。
- **比对先行**。Garmin 对重复上传返回 409 拒绝而不是覆盖，所以必须先拉现有活动清单、按开始时间 ±120s 匹配、按时长/距离/轨迹判定完整性，再决定传什么、删什么。
- **幂等账本**。SQLite 记录每个 workout 的上传状态，中断重跑不会重复。

## 踩坑实录

### 坑 1：国区账户，全球端点

用全球端点登录，SSO 认证一路成功，token 也拿到了，然后所有 API 调用 401。debug 日志里躺着真正的死因：

```
DI token refresh failed: 400
body: {"error":"invalid_grant",
 "error_description":"User doesn't exist in DB for GarminGUID: xxx"}}
```

账户是国区的（garmin.cn），数据在中国区服务器上。全球 SSO 接受你的密码，但全球业务数据库里查无此人。**症状极其迷惑：登录「成功」，调用全 401，报错还写着 Invalid Username or Password**——我的第一版代码在 token 失败后用假凭据重登，把这个真实错误完全掩盖了。

修复：登录时把区服持久化，之后所有命令自动走对端点。如果你的账户是国区的，`f2g login --cn` 一次即可。

### 坑 2：接口字段结构和文档对不上

这是最隐蔽的一个。garminconnect 的文档和示例都基于**详情接口**的字段结构（`summaryDTO.duration`、`activityTypeDTO.typeKey`），而**活动清单接口**把 `distance`/`duration` 放在了顶层，类型是 `activityType.typeKey`，轨迹有无看 `hasPolyline`。

我的解析器按文档写，结果清单数据全部解析成 `None`——比对逻辑退化到兜底分支，把 80 条**本来完整**的活动误判成「残缺待替换」。如果直接照那个计划执行，会删掉 80 条好数据再传一遍。

教训：**对外部 API 的每个字段假设，都要用真实响应验证一遍**。修复后重新比对，replace 从 80 变成 0——之前手动导入担心的问题其实不存在，真正的碎片另有其人（见下）。

### 坑 3：Keep 的双写，心率偷渡

真实数据教我做人的时刻。我有几年的训练是用 Keep 记录的，Keep 往苹果健康里**同一次训练写两条**：一条汇总壳（无心率无轨迹），一条详细版。我的解析器把心率挂到「包含该时间点的训练窗口」——但两个窗口重叠时，它只挂给后开始的那条。

结果：**详细版的心率被偷渡进了空壳**。870 个 FIT 文件里有 80 条训练丢了心率，而它们的空壳孪生兄弟却揣着完整心率躺在丢弃名单里。修复后 FIT 数量从 870 变 950，80 条训练的心率失而复得。

配套还加了去重：同类型、重叠超过较短一方 80% 的判为同一次训练的孪生，保留信息量大的（有 WorkoutStatistics/轨迹/心率者优先）。我的数据里折叠了 161 条空壳。

### 坑 4：文件名碰撞，静默覆盖

最后收尾时发现 FIT 文件数对不上：950 次写入只剩 870 个文件。Keep 的孪生对里有些**开始时间精确到秒都相同**，而文件名只含开始时间+类型——后写的覆盖先写的。

逐对核验后确认这次运气好：80 组碰撞里留下的恰好都是保留的那条更完整的版本，上传数据零损失。但这种「运气好」不能留给下一个用户——文件名加上了结束时间，彻底消除碰撞。

### 坑 5：Apple 2026 导出格式，静默瘦身

第一轮 789 条全部传完、0 失败，抽查 Garmin App 却发现：不少训练距离显示 `-- km`。回头翻 `export.xml` 才发现 Apple 在 2026 年换了导出格式：

- `duration` 改成了 `durationUnit="min"` 的分钟数（老格式是秒数）
- `<Workout>` 顶层的 `totalDistance`/`totalEnergyBurned` 属性**没了**，距离/卡路里搬进了 `<WorkoutStatistics>` 子元素（`sum` + `unit`）
- 暂停事件从 `pause`/`resume` 变成了 `HKWorkoutEventTypeMotionPaused`/`MotionResumed`

我的解析器按老格式读，距离卡路里全是 0——**解析不报错、上传也成功，只是数据悄悄缺了一块**。GPS 训练靠 Garmin 服务端从轨迹反算距离看不出来，纯心率训练就永远 `-- km`。修复解析器、删掉 789 条重传一遍，距离/卡路里/暂停分段才真正到位。

教训：**「上传成功」不等于「数据完整」，上传后必须抽查终端显示**。而格式变更这种事，Apple 不会在任何 changelog 里告诉你。

### 坑 6：Garmin 的时区显示，匹配器的陷阱

重传后核对账目，比对逻辑报告还有 85 条「Garmin 里没有」。逐条排查发现它们全部是我 2021 年在越南录的训练——开始时间和 Apple 导出**整整差一小时**，但换算成 UTC 时刻精确到秒完全一致。

原因是 Garmin 很聪明：它会按 GPS 轨迹位置把活动显示**当地时间**（越南 UTC+7，我常驻 UTC+8）。数据本身一个字节都没错，错的是我的比对逻辑——用裸本地时间对表，遇到跨时区训练必然误判。

修复：比对改用 UTC 绝对时刻（Garmin 的 `startTimeGMT` 对 Apple 导出里的带时区时间）。顺带发现早期删除脚本也因此漏删过 54 条，全是同一个原因。

教训：**凡是比较两个来源的时间戳，先统一到 UTC 再比**。本地时间只是显示层，当真就输了。

### 附带发现：重复上传的语义

一开始担心「之前手动导入的残缺数据会被覆盖吗」——答案是不会，Garmin 按开始时间返回 409 直接拒绝。所以正确的姿势是**盘点 → 删碎片 → 再上传**，而不是无脑重传。最终清理掉 127 条 2021–2025 年间的 `other` 类型碎片（就是当年手动导入的残骸，中位时长 10 分钟、几百米、全部自动命名）。同时确认 2025 年 12 月起的手表原生活动结构上就不可能被误伤。

## 结果

| 操作 | 结果 |
|---|---|
| 训练活动 | 789 条上传成功（含 GPS 502 条），0 失败 0 重复 |
| 体重记录 | 68 条全部推送 |
| 碎片清理 | 127 条删除 |
| 保留不动 | 80 条原完整活动 + 245 条手表原生活动 |

其中训练活动经历了一轮完整返工：第一版因坑 5 缺距离/卡路里，全部删除后用修复版重传（删除 789 + 重传 789 + 顺带替换 2 条旧残缺导入，均 0 失败）。最终用 UTC 比对核账：upload=0、replace=0，全部对得上。

上传全程约 26 分钟（2 秒/文件节流），没触发限流。中断可重跑，账本保证幂等。

## 续章：把 Keep 的历史找回来

Apple 迁移收官后，我发现还有一个时间段的记忆是空的：**2021 年换 Apple Watch 之前用 Keep（手机）记录的那批运动**——早期没戴表的步行、还有后来戴表但没进苹果健康的健身课。Keep 里还有一批和 Garmin 重复的历史（Apple Watch 时期双写的、换 Garmin 手表后同步的），要做的是去重后只补缺口。

Keep 的「数据导出」给两样东西：一份 xlsx（每条运动一行：时长/起止/卡路里/距离/心率序列）和一个 zip（1223 个 FIT 文件）。上手先考古了一圈，发现这导出比看起来有意思得多：

- zip 里每个 FIT 只有 ~180 字节——**纯摘要**（file_id + sport + session：开始时刻、时长、距离、均/最大心率），没有 record、没有轨迹。轨迹字段是一张带水印的静态地图 jpg，纯属装饰。
- xlsx 里的心率序列是**纯数字数组，没有时间戳**，只能按训练时长均匀铺回去。而且健身课的序列经常整个数组全是 0——Keep 根本没采到，只是占了个位。
- FIT 文件名里的中文走了 UTF-8 flag，macOS 自带的 `unzip` 直接「Illegal byte sequence」罢工；Python 的 `zipfile` 倒是好好的。
- FIT 内嵌的 UTC 开始时刻是全导出里唯一权威的时间源——和 Garmin `startTimeGMT` 逐秒比对，偏移直方图 1010/1016 条为 0（连我在越南旅行期间记录的都对得上），可以放心当匹配基准。

### 坑 7：Keep 的双写垃圾，上轮迁移还帮忙带进了 Garmin

写匹配器之前先看偏移直方图，顺手扫了一眼已配对活动的时长——扫出 54 条 **18~35 小时的「跑步」**。距离 5~8km、无 GPS、无心率，时长却是实际值的几十倍。溯源发现链条是：Keep 在苹果健康里写 summary shell（elapsed 虚高）+ detailed 两条记录；上轮 Apple 迁移时 `_dedupe_apple` 折叠了 detailed、把 shell 当真数据传了上去——**我上一章亲手把垃圾搬进了 Garmin**。

好在这正好是 Keep 补迁能修的：Keep 导出里有真实那条（正确时长 + 心率序列 + 距离）。这 54 条走了和当年一样的「删旧传新」流程，比如 2022-04-24 那次夜跑，Garmin 里显示 18.4 小时，Keep 说 54 分钟 10.2km、带 642 个心率采样——替换后三项全对。

同一机制还有两个变体值得记：Keep 导出**内部**也有双写（同秒开始、一条真实一条 18 小时假壳，只有一对），识别规则定为「同类型、同分钟内、时长 >4h 且 >3 倍」；另有 5 条漏网——3 条是 Keep 自己的「忘停记录」（12~22 小时的行走，GPS 轨迹只有 1km，连 Keep 端数据都是垃圾，没有干净替换源，认损删掉保时长统计干净）。

教训：**双写 App 的数据，每一条都要先问「这是真记录还是壳」**。壳的特征很稳定：elapsed 虚高几十倍、无细节采样，而真实的时长/距离自洽。

### 坑 8：409 还有第二种语义——时间子集

上传 251 条（197 新增 + 54 替换）回来 244 成功、**7 条 409**。第一反应是去查重复判定漏了什么，逐条核对才发现这 7 条全是同一个形态：Keep 的健身课，恰好是 Garmin 里某条**更长的行走活动的尾段子集**——开始晚 3~15 分钟，**结束时刻精确到秒相同**（Keep 把行走末段的拉伸/力量环节单独记了一节，Apple Watch 则把整段录成一次行走）。Garmin 的 409 不只挡「同一次活动重传」，还挡「时间上被现有活动包含的新活动」。

这次这个拒绝是**对的行为**：该时段在 Garmin 里已有更完整的记录，Keep 版本没有心率没有距离，硬塞进去只会重叠。所以正确响应不是重试也不是绕过，而是接受——我把它记成账本里的 `duplicate`，终态不留遗憾。

教训：**409 之后别急着当失败处理，先弄清它挡的是哪种重复**。是同活动的重传就查账本，是时间子集就说明服务器已有更完整的记录。

### 去重判定

匹配口径沿用主线的 UTC ±120s 一对一，加了三条例外规则，每条都对应一类真实数据形态：

| 规则 | 动机 |
|---|---|
| 跑步额外匹配 `treadmill_running` | 换 Garmin 后的跑步机跑步，Keep 端类型就是「跑步」，时长逐秒一致 |
| 健身课按时间重叠 ≥80% 匹配任意类型 | Apple Watch 时期 Keep 健身被记成 `other`/`swimming`/`gym` 等，类型对不上但时长逐秒一致 |
| 带 GPS 的现有活动永不替换 | GPS 轨迹是 Keep 导出里没有的资产，宁可留着垃圾时长也不能丢轨迹（保住了 2 条） |

结果：1223 条 → **197 上传、962 跳过、54 替换、9 条 <60s 碎片、1 条内部幽灵壳**。

### 续章结果

| 操作 | 结果 |
|---|---|
| Keep 独有活动 | 197 条计划上传：190 成功 + 7 条被 409 正确拒绝（时间子集） |
| 垃圾时长修复 | 54 条删旧传新（时长、距离、心率全部补齐）+ 5 条无替换源直接删除 |
| 终态核账 | 1299 条活动、0 条超 4 小时的跑步/行走，UTC 抽查 5 条全对 |
| 类型归属 | Keep 行走被 Garmin 归为 Hiking、健身归为 Strength Training，数据字段无误 |

上传约 9 分钟（251 个文件、2s 节流）。账本用 `keep@编号` 前缀记账，与 Apple 流水线互不干扰，幂等可重跑。

值得一提的是主线的一个「已知限制」在这里被顺手解掉了：**无心率无轨迹的训练**（未戴表时 Keep 记的健身课）本来无法生成 FIT——但 Keep 自己导出的摘要 FIT 本身就是合法活动文件，直接用它上传，Garmin 照样收（时长/卡路里/均最大心率都在）。所以 Keep 流水线对这类记录走双路：有心率的用 xlsx 重建带 record 的 FIT，没有的用 bundle FIT 原样上。

## 局限（重要）

- **步数/睡眠/HRV/每日心率无法迁移**——没有写入 API，这是 Garmin 的硬限制，不是工具问题
- 无心率无轨迹的训练（未戴表时第三方 App 记的）无法生成 FIT
- 非官方 API 有被封风险，工具层面做了节流和 429 退避，但无法根除

## 工具

整个流水线开源在 [vectorstone/fitness2garmin](https://github.com/vectorstone/fitness2garmin)：纯 Python，核心依赖只有官方 garmin-fit-sdk 和 garminconnect，离线集成测试覆盖解析/编码/比对全链路（不需要真实账户就能跑）。用法见 README。

一句话总结这次的经验：**迁移工具的价值不在「能传」，而在传之前把「该传什么」算清楚**——字段解析、重复判定、区服端点，这些看不见的部分才是翻车重灾区。
