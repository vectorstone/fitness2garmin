# 把五年的 Apple Watch 健身数据完整搬进 Garmin Connect

> 一次真实的数据迁移记录：981 条训练、五年历史、零失败。顺便把过程中的四个坑（两个足以让任何现成教程方案翻车）完整记下来。
>
> 配套工具已开源：[fitness2garmin](https://github.com/vectorstone/fitness2garmin)。

## 背景

我戴了几年 Apple Watch，最近换成了 Garmin。新表很好，但五年的跑步、骑行、力量训练历史还锁在苹果健康里。Apple Watch 换机不丢数据的前提是继续用 Apple 生态，而 Garmin 那边只认自己的格式。

Garmin Connect 网页端有个「导入数据」入口，但只接受 Fitbit 格式的 CSV，而且一次只能导一年、只有每日汇总（步数/体重），**训练活动本身根本进不去**。手动试过一些第三方方案，结果导入了一堆残缺数据——有轨迹没心率、时长对不上的碎片，一度想放弃。

于是决定自己搭一条流水线：**提取 → 转换 → 批量静默上传**。

## 先说结论

- 没有任何现成工具能一步到位，但三段各有成熟组件，组装起来比想象中可靠
- 最终 789 条训练 + 68 条体重记录全部迁移成功，0 失败、0 重复，顺带清掉了 127 条历史残留碎片
- 全程踩了四个坑，每一个都值得单独记录——如果你也想做同样的事，大概率会全部遇到

## 调研：为什么没有现成工具

动手前我把 GitHub 上能找到的相关项目扫了一遍（36 个候选逐个读源码验证），生态现状是：

1. **上传库的格局在 2026 年洗过一次牌**。曾经的事实标准 `garth` 在 2026 年 3 月被官方废弃——Garmin 改了认证流程，Cloudflare 对旧 SSO 端点直接 429。现在能用的只有 [python-garminconnect](https://github.com/cyberjunky/python-garminconnect) 0.3.20+（模拟移动端 TLS 指纹，活跃维护）。所有还依赖 garth 的老教程和老项目，登录环节已经全灭。
2. **Garmin 官方 API 帮不上忙**。2026 年 10 月新开的官方 Personal API 是只读的；Health API 的写入权限只对企业合作开放。个人用户的「调 API 上传」实际就是走非官方客户端，和你手机上的 Garmin Connect App 打同一套端点。
3. **每日指标是死路**。步数、睡眠、HRV 没有任何 API 写入通道（官方非官方都没有），能写的只有体重/身体成分。凡是宣称能把每日数据同步过去的工具，要么走网页导入，要么在吹牛。
4. **解析侧没有好用的**。Apple 的 `export.xml` 有两个陷阱：训练心率被聚合成 ~15 分钟块（所以必须用 Record 级心率样本重新贴回训练窗口）；GPS 轨迹单独放在 `workout-routes/*.gpx`，靠 `<Workout>` 里的 FileReference 关联。现有的解析器要么只出 CSV，要么内存爆炸。

所以方案定型为：**自己写流式解析器 + 官方 garmin-fit-sdk 编码 + python-garminconnect 上传**，再加一层比对计划保证幂等和增量。

## 流水线设计

```
export.zip ──流式解析──▶ workouts.json ──FIT 编码──▶ data/fit/*.fit
                │                                          │
                │                                     比对计划 plan.json
                ▼                                          │
        Garmin 现有活动清单 ◀──inventory──┘          upload / replace / skip
                                                           │
                                              静默批量上传（token 缓存、
                                              409 去重、2s 节流、SQLite 账本）
```

几个关键设计决策：

- **解析必须流式**。我的 `export.xml` 解压后约 700MB，全量加载必死。用 `iterparse` 两遍流式（第一遍收训练，第二遍收窗口内心率），内存峰值稳定在几十 MB。
- **心率归属**。心率样本按时间窗口挂回训练——这个看似简单的逻辑后面藏着坑 3。
- **比对先行**。Garmin 对重复上传返回 409 拒绝而不是覆盖，所以必须先拉现有活动清单、按开始时间 ±120s 匹配、按时长/距离/轨迹判定完整性，再决定传什么、删什么。
- **幂等账本**。SQLite 记录每个 workout 的上传状态，中断重跑不会重复。

## 踩坑实录

### 坑 1：国区账户，全球端点

用全球端点登录，SSO 认证一路成功，token 也拿到了，然后所有 API 调用 401。debug 日志里躺着真正的死因：

```
DI token refresh failed: 400
body: {"error":"invalid_grant",
 "error_description":"User doesn't exist in DB for GarminGUID: xxx"}}
```

账户是国区的（garmin.cn），数据在中国区服务器上。全球 SSO 接受你的密码，但全球业务数据库里查无此人。**症状极其迷惑：登录「成功」，调用全 401，报错还写着 Invalid Username or Password**——我的第一版代码在 token 失败后用假凭据重登，把这个真实错误完全掩盖了。

修复：登录时把区服持久化，之后所有命令自动走对端点。如果你的账户是国区的，`f2g login --cn` 一次即可。

### 坑 2：接口字段结构和文档对不上

这是最隐蔽的一个。garminconnect 的文档和示例都基于**详情接口**的字段结构（`summaryDTO.duration`、`activityTypeDTO.typeKey`），而**活动清单接口**把 `distance`/`duration` 放在了顶层，类型是 `activityType.typeKey`，轨迹有无看 `hasPolyline`。

我的解析器按文档写，结果清单数据全部解析成 `None`——比对逻辑退化到兜底分支，把 80 条**本来完整**的活动误判成「残缺待替换」。如果直接照那个计划执行，会删掉 80 条好数据再传一遍。

教训：**对外部 API 的每个字段假设，都要用真实响应验证一遍**。修复后重新比对，replace 从 80 变成 0——之前手动导入担心的问题其实不存在，真正的碎片另有其人（见下）。

### 坑 3：Keep 的双写，心率偷渡

真实数据教我做人的时刻。我有几年的训练是用 Keep 记录的，Keep 往苹果健康里**同一次训练写两条**：一条汇总壳（无心率无轨迹），一条详细版。我的解析器把心率挂到「包含该时间点的训练窗口」——但两个窗口重叠时，它只挂给后开始的那条。

结果：**详细版的心率被偷渡进了空壳**。870 个 FIT 文件里有 80 条训练丢了心率，而它们的空壳孪生兄弟却揣着完整心率躺在丢弃名单里。修复后 FIT 数量从 870 变 950，80 条训练的心率失而复得。

配套还加了去重：同类型、重叠超过较短一方 80% 的判为同一次训练的孪生，保留信息量大的（有 WorkoutStatistics/轨迹/心率者优先）。我的数据里折叠了 161 条空壳。

### 坑 4：文件名碰撞，静默覆盖

最后收尾时发现 FIT 文件数对不上：950 次写入只剩 870 个文件。Keep 的孪生对里有些**开始时间精确到秒都相同**，而文件名只含开始时间+类型——后写的覆盖先写的。

逐对核验后确认这次运气好：80 组碰撞里留下的恰好都是保留的那条更完整的版本，上传数据零损失。但这种「运气好」不能留给下一个用户——文件名加上了结束时间，彻底消除碰撞。

### 附带发现：重复上传的语义

一开始担心「之前手动导入的残缺数据会被覆盖吗」——答案是不会，Garmin 按开始时间返回 409 直接拒绝。所以正确的姿势是**盘点 → 删碎片 → 再上传**，而不是无脑重传。最终清理掉 127 条 2021–2025 年间的 `other` 类型碎片（就是当年手动导入的残骸，中位时长 10 分钟、几百米、全部自动命名）。同时确认 2025 年 12 月起的手表原生活动结构上就不可能被误伤。

## 结果

| 操作 | 结果 |
|---|---|
| 训练活动 | 789 条上传成功（含 GPS 502 条），0 失败 0 重复 |
| 体重记录 | 68 条全部推送 |
| 碎片清理 | 127 条删除 |
| 保留不动 | 80 条原完整活动 + 245 条手表原生活动 |

上传全程约 26 分钟（2 秒/文件节流），没触发限流。中断可重跑，账本保证幂等。

## 局限（重要）

- **步数/睡眠/HRV/每日心率无法迁移**——没有写入 API，这是 Garmin 的硬限制，不是工具问题
- 无心率无轨迹的训练（未戴表时第三方 App 记的）无法生成 FIT
- 非官方 API 有被封风险，工具层面做了节流和 429 退避，但无法根除

## 工具

整个流水线开源在 [vectorstone/fitness2garmin](https://github.com/vectorstone/fitness2garmin)：纯 Python，核心依赖只有官方 garmin-fit-sdk 和 garminconnect，离线集成测试覆盖解析/编码/比对全链路（不需要真实账户就能跑）。用法见 README。

一句话总结这次的经验：**迁移工具的价值不在「能传」，而在传之前把「该传什么」算清楚**——字段解析、重复判定、区服端点，这些看不见的部分才是翻车重灾区。
